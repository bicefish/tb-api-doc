Document Maintenance

Changelog

This page documents changes to the HTML documentation of the technikboerse interfaces. It serves editorial traceability and makes visible when structural, functional, or technical adjustments were made.

Page Goal Make changes to document structure, content, and known discrepancies traceable.
Particularly Relevant for Editorial team, product management, support, integrators, and quality assurance.
Core Principle Not only technical changes but also documentary clarifications are versioned.

Purpose and Usage

Traceability

Changes to the interface documentation should be transparent. This applies to both new content and corrections, clarifications, and documented Known Issues.

Distinction from Known Issues

The known-issues page describes operational or functional discrepancies. The changelog documents when and why these topics were included, adjusted, or cleared in the documentation.

Maintenance during Ongoing Operations

Every content-relevant change to structure, reference pages, example pages, or references should be recorded with date, scope, and brief justification.

Important

The changelog should not only contain major releases. Even smaller clarifications can be relevant for integrators if they affect functional logic, validation, or example interpretation.

Maintenance Principles

Principle 1: Version Functional Changes

Changes to processing logic, field meanings, mandatory information, or deletion semantics must always be recorded in the changelog.

Principle 2: Also Record Documentary Clarifications

Even changes that do not change any interface function but reduce room for interpretation should be documented.

Principle 3: Cross-reference Known Issues

If a Known Issue is newly added, changed, or cleared, this should be visible in the changelog and refer to the affected page.

Principle 4: Identify Structural and Design Changes

Major changes to navigation, CSS, page naming, or linking should be recorded as separate entries, even if they are functionally neutral.

Open Points

Link and Concretize API Reference

The REST API overview page already refers to a technical reference. Its current scope, endpoint coverage, and release status should still be editorially verified.

Clarify status of validation

The element validation is present in the XSD but has not yet been operationally fully clarified. As soon as a decision is available, it should be documented in the changelog.

Concretize Optional Additional Objects

For auction and purchase, the current functional level of use should be checked and, upon clarification, recorded as a change event.

Define Versioning Model

The version numbers used here are a practical starting point. For ongoing operations, a binding versioning model should be defined.
