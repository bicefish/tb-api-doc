Normative XML Reference

Element ad

The element ad represents a single ad within the XML Exchange. It contains the technical identity of the ad, its categorization, as well as information relevant for presentation, search, pricing, media, and contacting. For integrators, ad is the central functional data record of the interface.

Particularly Relevant for Systems that import, update, delete, or enrich ads with prices, images, and contact persons.
Core Content guid, id, category_id, contact_ids, created, modified, images, price

Functional Role

ad describes a marketed object such as a machine, a spare part, or another tradable inventory item within technikboerse.

Technical Role

The target system uses guid, id, and category_id to uniquely locate, update, and correctly classify the ad.

Context

An ad is functionally always in the context of a dealer object and can refer to contacts, prices, media, and additional objects.

Schema

Attributes of ad

Attribute Meaning Required Note
guid Unique technical identification of the ad. Yes Decisive for stable assignment in the target system.
id Internal ID of the ad in the sending system. Yes Serves as an additional reference alongside the GUID.
category_id Unique assignment of the ad to a category. Yes Normatively relevant for classification in the target system.
category_name Readable name of the category. Optional Helpful for plausibility checks and manual verification, but not decisive for technical assignment.
parent_category_name Readable name of the parent category. Optional Primarily for orientation and traceability.
ad_type Type of ad, e.g., machine or spare part context. Optional or context-dependent Should be documented and evaluated if different functional flows depend on it.

Important: category_id is Normative

For the technical assignment of an ad, the category_id is decisive. Readable fields such as category_name or parent_category_name are helpful for control and diagnosis, but do not replace the unique category ID.

Logic

Processing Rules

Rule 1: Locate Ads Primarily via GUID

The target system should identify an ad primarily via guid. The id serves as an additional reference to the sending system.

Rule 2: Control Category Assignment Technically via category_id

The classification of the ad must not rely solely on readable names. The technical category ID is authoritative.

Rule 3: Evaluate Changes via modified

In update processing, modified is the central field for deciding whether an ad can be adopted or skipped.

Rule 4: Interpret Contacts Only as Referenced

In contact_ids, only references are maintained. The actual contact person data is located at the dealer level in contacts and must be resolved there.

Rule 5: Treat Media and Price Objects as Own Sub-areas

Price, image, and video objects should be processed structurally in the target system. Flat or lossy adoption makes later extensions and validations more difficult.

Rule 6: Observe Deletion Logic Separately

The absence of an ad in an Update Mode is not automatically a deletion. Deletion cases are signaled separately at the root level or result from the completeness of the inventory in Full Syncs.

Syndication

Forward Interfaces & Downstream Publication

An optional forwarding block can be used to control the publication of the ad on connected, downstream platforms.

Optional Nature & Default Behavior

Controlling forwarding is optional. If the corresponding block is missing, the default behavior configured in the system applies, which usually means "no change" to the existing status.

Configuration Dependency

The actual execution of the forwarding is subject to the booked product and dealer configuration. Targets must correspond to a documented, agreed catalog (source of truth).

Example: Forwarding Block

<exports>
  <export target="portal_a" publish="true" />
  <export target="portal_b" publish="false" />
</exports>
Data Quality

Mapping, Fallbacks & Standardization

To ensure data quality when importing ads, various data points go through a normalization and mapping process.

Category Assignment & Fallbacks

Categories are primarily assigned based on the category_id. If the assignment fails or the category is invalid, defined fallback rules apply (e.g. assignment to a parent category or "Other") to ensure the ad is not rejected.

Manufacturer Normalization

Manufacturer names are normalized (e.g. spelling mistakes corrected, aliases merged). If a manufacturer could not be resolved, fallback rules apply (e.g. "Other" or creation as free text), depending on system specifications.

Flexible Model Processing

Model names are processed flexibly. Often an attempt is made to match models from catalogs, but free-text adoption is supported if strict mapping is not possible.

Attribute Handling

Known and supported attributes are processed, unknown attributes or those not provided for in the schema are ignored (silent ignore) without causing the import to fail.

Standard vs. Custom Mapping

By default, adherence to the general data model is expected. Custom mapping agreements can be arranged, but they deviate from standard behavior. The integration partner is responsible for ensuring proper mapping alignment and delivering data in the agreed format.

Interpretation

The example shows an ad with technical identity, categorization, price, contact reference, and media link. In the target system, the unique assignment of the ad should occur first, followed by the adoption of functional content and linked sub-objects.

Best Practices

Notes and Pitfalls

Typical Error: Mapping Category via Name

If the assignment is made exclusively via readable category names, incorrect classifications can quickly arise. The category_id is authoritative.

Typical Error: Not Resolving Contact References

contact_ids do not contain complete contact person data. Without resolution against contacts, contact references remain incomplete.

Typical Error: Ignoring modified

If ads are blindly overwritten with every import, it creates unnecessary updates and possible side effects in downstream systems.

Documentation Note

Rarely used elements such as auction and purchase should not be removed from the documentation as long as they are still provided for in the XSD.
