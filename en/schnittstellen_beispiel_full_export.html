XML Example Page

Full Export

This page explains the Full Export based on a didactically reduced XML example. The goal is not to repeat the full XSD reference, but to present the functional processing model of a full inventory in an understandable and implementable way.

Page Goal Illustrate how a Full Export is structured and how it is to be interpreted functionally.
Particularly Relevant for Integrators, testers, and support when checking a full synchronization.
Core Point A Full Export represents the complete target inventory of the agreed transfer selection.

Classification

What a Full Export Means

The export contains all active advertisements of the agreed transfer selection. Objects that were previously known but no longer appear in the current file are functionally considered removed or inactive.

What a Full Export is Not

A Full Export is not a pure change set. The target system must not ignore missing objects, but must treat the delivered inventory as a complete reference state.

Relationship to Reference Documentation

The normative description of individual elements occurs on the pages for exchange, dealer, ad, and contact. This example page shows their interplay.

Didactically Reduced Full Export Example

<exchange>
  <senderName>provider-a</senderName>
  <exportDate>2024-05-12T06:00:00</exportDate>
  <transferMode>full</transferMode>
  <dealersDeleted />
  <adsDeleted />

  <dealers>
    <dealer guid="dealer-1001" id="1001">
      <info>
        ...
      </info>
      <created>2024-01-01T09:00:00</created>
      <modified>2024-05-12T06:00:00</modified>

      <contacts>
        <contact id="12">
          <first_name>Max</first_name>
          <last_name>Mustermann</last_name>
          <phone>+49 123 456789</phone>
          <email>max.mustermann@example.invalid</email>
          <languages_iso_639_1>en</languages_iso_639_1>
        </contact>
      </contacts>

      <ads>
        <ad guid="ad-5001" id="5001" category_id="210" category_name="Combine Harvester">
          <info>
            ...
          </info>
          <contact_ids>
            <contact_id>12</contact_id>
          </contact_ids>
          <price currency="EUR" taxtype="inclusive" tax_percentage="0.190">234567</price>
          <created>2024-01-10T10:00:00</created>
          <modified>2024-05-12T06:00:00</modified>
          <images>
            ...
          </images>
        </ad>
      </ads>
    </dealer>
  </dealers>
</exchange>
Area Interpretation Meaning for Target System
transferMode=full The file is to be understood as a complete inventory. Missing, previously known objects are to be treated functionally as removed or inactive.
dealersDeleted / adsDeleted empty No explicit deletion lists are provided. Cleanup occurs implicitly via the completeness of the delivered inventory.
dealer The dealer forms the framework for contacts and advertisements. Resolve dealer first, then process subordinate objects.
contact + contact_ids The advertisement refers to a contact person defined in the dealer context. Resolve contact ID within the dealer, do not interpret globally.
modified Shows the last modification time of the respective object. Can be used to optimize processing, but does not change the "full" character of the file.

Processing in Target System

Rule 1: Interpret File as Full Inventory

After evaluating transferMode=full, the target system must treat the file as the complete target state and not just update individual contained objects.

Rule 2: Root First, then Dealer, then Sub-objects

Processing should start with root metadata, then assign dealer objects, and only then process contacts and advertisements.

Rule 3: Clean Up Missing Objects

Objects that were present in previous Full Exports or local inventories but are missing in the current file must be treated as removed or inactive.

Rule 4: Resolve References Consistently

Contact references from contact_ids are to be resolved against the contacts defined in the dealer. Media, pricing, and category data should be adopted structurally.

Distinction from Update

Aspect Full Export Update Export
Basic Principle Complete target inventory Change set within a retrospective period
Missing Objects Considered removed or inactive Remain unchanged
backLogDays Not required Functionally relevant
Deletion Handling Primarily implicit via completeness Primarily explicit via deletion containers

Notes and Pitfalls

Typical Error: Treating Full like Update

If a Full Export is interpreted only as a collection of contained changes, outdated or actually removed objects erroneously remain in the target system.

Typical Error: Misunderstanding Empty Deletion Containers

Empty elements dealersDeleted or adsDeleted do not mean in a Full context that no cleanup is required.

Note on Didactics

The example shown here is deliberately reduced. For the complete technical structure, the reference pages and the XSD are authoritative.
