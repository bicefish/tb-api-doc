Processing Rule

Deletion Logic for XML Exchanges

This page describes how deleted dealers and ads are signaled in the technikboerse XML Exchange and what impact this has on the target system. The distinction between full and update is functionally decisive.

Particularly Relevant for Integrators of target systems that must keep inventories synchronized and correctly apply deletions.
Core Elements dealersDeleted, adsDeleted, deleteInfo, transferMode
Basics

Basic Rules

Behavior for transferMode=full

The export is to be understood as a complete target inventory. All active ads of the agreed transfer selection are included. Ads not included are considered inactive or deleted and must be removed or deactivated in the target system.

Behavior for transferMode=update

The export is to be understood as a change set. Only new, changed, or deleted objects within the lookback period are transferred. Deletions are explicitly signaled via dealersDeleted and adsDeleted.

Important

Empty deletion containers do not automatically mean that no inventory cleanup is required in every case. In full mode, cleanup results from the completeness of the delivered inventory, not from an explicit deletion list.

Operational Context

The choice between Full and Update modes is closely linked to your transfer method and processing frequency. Details on the impacts on performance and currency can be found in the Transport and Operating Model section.

Schema

Relevant Elements

Element Meaning Usage Note
dealersDeleted Container for dealers deleted in the relevant period. Primarily relevant for update. Can be empty. In full mode, it is usually not decisive for cleanup.
adsDeleted Container for ads deleted in the relevant period. Primarily relevant for update. Can be empty. In update mode, contained entries must be explicitly processed.
deleteInfo Structural element for individual deletion information within deletion containers. Schema-relevant. Should be documented even if not prominently visible in the examples.
transferMode Controls the interpretation of the file. Always relevant. Without correct evaluation of this field, the deletion logic cannot be implemented correctly from a functional perspective.
Implementation

Processing in the Target System

Rule 1: Determine Mode First

Before any deletion processing, the target system must evaluate transferMode. Only then is it clear whether the file represents a full inventory or just a change set.

Rule 2: For Full, Do Not Just Evaluate Deletion Containers

For full, all previously known objects that are no longer included in the current export must be treated as removed or inactive. The completeness of the export is the normative basis here.

Rule 3: For Update, Apply Only Explicit Changes

For update, only the transferred new, changed, or deleted objects may be processed. Objects not included remain unchanged in the target system.

Rule 4: Treat Dealer and Ad Deletions Separately

Deletions of dealers and ads should not be mixed in the target system. A deleted dealer can have different functional effects than a single deleted ad.

Rule 5: Process Deletions Idempotently

The target system should process deletions such that re-processing the same deletion instruction does not produce any undesired side effect.

Rule 6: Observe Lookback Period for Update

For update, backLogDays must also be considered. The export can contain deletions that fall within this defined lookback period.

Business-Critical Point

The most common functional misimplementation is to treat an update file like a full inventory. This results in datasets being deleted in the target system that are actually only not included because they have not changed in the period under consideration.

Effect Types

Deleted Ad

An entry in adsDeleted signals that an existing ad must be removed, deactivated, or otherwise marked as no longer active in the target system.

Deleted Dealer

An entry in dealersDeleted signals that a dealer object is no longer active. Depending on target system logic, this may also affect assigned ads.

No Longer Included in Full

If a previously known object is no longer included in a Full Sync, this is considered a functional deletion or inactivation case, even if no explicit entry exists in a deletion container.

XML

Examples

Mini-Example: Update with Deleted Ad

<exchange>
  <senderName>provider-a</senderName>
  <exportDate>2024-05-12T06:00:00</exportDate>
  <transferMode>update</transferMode>
  <backLogDays>3</backLogDays>
  <dealersDeleted/>
  <adsDeleted>
    <deleteInfo guid="ad-4711" id="4711" />
  </adsDeleted>
  <dealers>
    ...
  </dealers>
</exchange>

The target system must treat the ad with the referenced identity as deleted or inactive.

Mini-Example: Update with Deleted Dealer

<exchange>
  <senderName>provider-a</senderName>
  <exportDate>2024-05-12T06:00:00</exportDate>
  <transferMode>update</transferMode>
  <backLogDays>3</backLogDays>
  <dealersDeleted>
    <deleteInfo guid="dealer-99" id="99" />
  </dealersDeleted>
  <adsDeleted/>
  <dealers>
    ...
  </dealers>
</exchange>

The target system must treat the referenced dealer as deleted or inactive and consider its own follow-up logic for associated ads.

Mini-Example: Full Sync with Implicit Cleanup

<exchange>
  <senderName>provider-a</senderName>
  <exportDate>2024-05-12T06:00:00</exportDate>
  <transferMode>full</transferMode>
  <dealersDeleted/>
  <adsDeleted/>
  <dealers>
    <dealer guid="dealer-1" id="1">
      ...
    </dealer>
  </dealers>
</exchange>

A previously known ad that is no longer included in this Full Sync must be treated as removed or inactive in the target system, even if adsDeleted is empty.

Best Practices

Typical Errors and Misinterpretations

Error 1: Treating Update Like Full

Objects not included are deleted, even though they just haven't changed. This leads to data loss and inconsistent inventories in the target system.

Error 2: Overestimating Deletion Containers in Full

The target system relies exclusively on dealersDeleted or adsDeleted. In full mode, however, the total amount of included datasets is decisive.

Error 3: Not Distinguishing Dealer and Ad Deletions

A deleted dealer is treated like a single deleted ad or vice versa. This creates incorrect functional follow-up effects.

Error 4: Ignoring backLogDays

In update processes, it is not taken into account that deletions within a defined lookback period can be redelivered.
