Normative XML Reference

Element contact

The element contact represents a contact person at the dealer level. Contacts are defined within a dealer object and can be assigned to individual ads via contact_ids. Thus, contact forms the bridge between organizational responsibility and concrete contactability within the interface.

Particularly Relevant for Integrators who process contact persons, responsibilities, languages, and contact references to ads.
Core Content id, gender, first_name, last_name, phone, mobile, email, responsibilities, languages_iso_639_1

Structure and Classification

  </contact>

Functional Role

contact describes a specific contact person for dealers or ads, for example for used machines, new machines, or spare parts.

Technical Role

Contacts are defined within a dealer and referenced via their id from within the ad.

Multilingualism and Responsibilities (Entity Roles)

A contact bundles functional roles (responsibilities) and language profiles. These attributes serve for classification and should not be merged into free text fields in the target system.

Known Discrepancy: mobile vs. mobil

In the XSD, the field mobile is provided. In the available Full and Update examples, mobil is used instead. This discrepancy is schema-relevant and should be additionally reported separately in the online documentation on the /interfaces/xml/known-issues page.

Connectivity

Assignment to Ads

Definition

Contacts are defined in the dealer object under contacts and receive their unique id there.

Referencing

Ads refer to these IDs via contact_ids. This allows one contact person to be assigned to multiple ads.

Processing

The target system must resolve the contact IDs against the contact definitions of the respective dealer and must not misunderstand these references as independent contact objects.

Logic

Processing Rules

Rule 1: Resolve Contacts within the Dealer Context

The id of a contact is to be interpreted in the context of the dealer. A global resolution without dealer reference can lead to incorrect assignments. It must serve as a stable, unique identifier per dealer.

Rule 2: Ensure Reference Consistency (No Dangling References)

Ads may only reference IDs in contact_ids that are actually defined in the dealer object under contacts. The target system must safely handle missing references.

Rule 3: Inheritance Logic & Fallbacks

An explicit assignment of contacts at the ad level (contact_ids) overrides any default contacts at the dealer level. If an ad assignment is missing, the defined default dealer contact applies (fallback).

Rule 4: Process Languages Normatively

Language information (languages_iso_639_1) MUST be processed as standardized ISO-639-1 codes to enable automated routing and correct front-end output.

Rule 5: Use Responsibilities as Classification

The responsibilities field defines functional roles (e.g., "Used Machines", "New Machines"). It must be evaluated for correct routing classification and not as unstructured free text.

Rule 6: Handle Schema Discrepancies Visibly

Discrepancies such as mobil instead of mobile must not be silently ignored, but should be operationally documented and deliberately considered during implementation.

XML

Example

Minimal Example

<contact id="12">
  <gender>male</gender>
  <first_name>Max</first_name>
  <last_name>Mustermann</last_name>
  <phone>+49 123 456789</phone>
  <mobile>+49 171 1234567</mobile>
  <email>max.mustermann@example.invalid</email>
  <responsibilities>
    ...
  </responsibilities>
  <languages_iso_639_1>en</languages_iso_639_1>
</contact>

Interpretation

The example shows a contact person with personal contact information, language assignment, and area of responsibility. In the target system, this record should be stored within the dealer context and made referencable from the ads via contact_ids.

Best Practices

Notes and Pitfalls

Typical Error: Interpreting Contact ID Globally

If the id of a contact is interpreted system-wide instead of dealer-specifically, contacts can be inadvertently assigned to the wrong ads or dealers.

Typical Error: Expecting Contact Person Data Directly in the Ad

The ad contains only references in contact_ids. Without resolution against contacts, contact person information remains incomplete.

Typical Error: Transforming Language Codes into Free Text

If language codes are not adopted normatively, it complicates later filter and routing logic.

Note on Known Issues

Example/schema discrepancies such as mobil instead of mobile should additionally be collected centrally on the /interfaces/xml/known-issues page.
