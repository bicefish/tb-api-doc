Structure & Reference

XML Structure & Root Element

This page explains the general structure of the XML document and describes the root element exchange. This element serves as the common container for all transferred data and contains the global metadata required to control the exchange process.

The document acts as a central entry point for understanding the logical relationships between metadata, dealers, contacts, and ads before diving into the detailed references for individual objects.

Import and Export Perspective

The XML interface supports two major directions: Import (into technikboerse) and Export (from technikboerse). Please note that the semantics of the XML elements must always be read from the perspective of the respective receiving or sending system.

For the import process, the Import XML schema, Example file for full import, and Example file for update import are available as accompanying schema/example artifacts.

Target Audience Integrators, developers of import interfaces, support.
Relevant Fields senderName, exportDate, transferMode, backLogDays, dealersDeleted, adsDeleted, dealers, validation
Orientation

General XML Structure

The XML document follows a clear hierarchical structure, combining a shared header for metadata with various functional sections. At the top level, you'll find metadata, transfer mode information, and optional deletion lists, followed by the actual dealer data with its nested objects. The following overview provides initial orientation; detailed field definitions are provided in the subsequent sections of this page and on the linked detail pages.

Abstract Visualization

  • exchange (Root Element)
    • • Metadata (Sender, Date)
    • • Transfer Mode (Full/Update)
    • • Deletion Lists (optional)
    • • dealers (Dealer List)
      • • dealer (Dealer)
        • • Master Data (Name, Address)
        • • contacts (Contact Persons)
        • • ads (Ad List)
          • • ad (Single Ad)

Simplified Example:

<exchange>
  <metadata />
  <transferMode />
  <dealersDeleted />
  <adsDeleted />
  <dealers>
    <dealer>
      <contacts />
      <ads>
        <ad />
      </ads>
    </dealer>
  </dealers>
</exchange>

Note: This is an abstracted representation for orientation purposes. For exact field names and validation rules, please refer to the field reference below.

Dictionary

Field Reference

exchange

Root element of the XML exchange file.

Type
Container element
Required
Yes
Contains
senderName, exportDate, transferMode, optional backLogDays, dealersDeleted, adsDeleted, dealers, optional validation
Processing Rule
The file is to be treated as a complete functional unit. Processing individual nodes without considering the root metadata is not sufficient.

senderName

Unique name of the file sender.

Type
String
Required
Yes
Meaning
Identifies the sending system. Depending on the direction, this field identifies either the partner (Partner → technikboerse) or technikboerse (technikboerse → Partner).
Processing Rule
The value should remain stable over the long term. Changes may result in known datasets no longer being correctly assigned or updated in the target system.

exportDate

Time of generation of the exchange file.

Type
Date/Time
Required
Yes
Meaning
Marks the creation time of the file.
Processing Rule
exportDate describes the file, not the modification time of individual objects. For object updates, the respective modified values are authoritative.

transferMode

Indicates the type of transfer.

Type
String
Required
Yes
Valid Values
full, update
Meaning
full stands for a complete synchronization, update for a change set.
Processing Rule
The receiving system must control the entire import logic based on this field.

backLogDays

Defines the lookback period for an update transfer.

Type
Integer
Required
No, only relevant for transferMode=update
Meaning
Specifies the period over which changes and deletions are included in the update.
Processing Rule
The field is only functionally relevant in the update context. It is not required for full transfers.

dealersDeleted

Container for dealers deleted in the relevant period.

Type
Container element
Required
Yes, but can be empty
Meaning
In update transfers, the element contains dealers deleted during the lookback period.
Processing Rule
In update mode, these dealers must be removed or deactivated in the target system. In full mode, the element is usually empty.

adsDeleted

Container for ads deleted in the relevant period.

Type
Container element
Required
Yes, but can be empty
Meaning
In update transfers, the element contains deleted ads.
Processing Rule
In update mode, these ads are to be specifically deleted or deactivated in the target system.

dealers

Container for the transferred dealer objects.

Type
Container element
Required
Yes
Meaning
Contains the actual payload of the exchange in the form of dealer objects with their ads and contact persons.
Link
/interfaces/xml/dealer, /interfaces/xml/ad, /interfaces/xml/contact

validation

Optional section for validation information.

Type
Container element
Required
Optional
Meaning
The element is provided for in the schema and should therefore be documented, even if it is often less prominent operationally.
Editorial Recommendation
The HTML documentation should clearly state whether the element is actively used, can be ignored, or is intended for extensions.

Important: senderName is identification-relevant

senderName is not just descriptive information, but a technical key in the exchange context. A subsequent change can lead to known datasets no longer being correctly assigned.

Rules

Processing Logic at the Root Level

Rule 1: Evaluate Root First

Before processing dealer or ad objects, at least senderName, transferMode, and exportDate must be evaluated.

Rule 2: Mode Determines Import Strategy

With full, the file is to be treated as a complete target state. With update, the file is to be processed as a delta-oriented change set.

Rule 3: Interpret Deletion Containers Only in Functional Context

Empty deletion containers do not automatically mean that no inventory cleanup is required. In full mode, cleanup primarily results from the completeness of the delivered inventory.

Rule 4: Do Not Confuse Root Metadata with Object Metadata

exportDate refers to the file. modified refers to individual objects. For object updates, the respective object values are authoritative.

Best Practice

Notes and Pitfalls

Known Issue / Testing Note

The example XMLs are not fully schema-compliant in all respects. Such discrepancies should not be treated in detail on this page, but should be transparently documented on the /interfaces/xml/known-issues page.

Typical Implementation Error

transferMode is ignored and every file is treated as a full inventory. This leads to incorrect deletions and faulty synchronization states for update files.

Typical Interpretation Error

exportDate is used as a criterion for object updates. However, the respective object fields such as modified are authoritative for updates to individual datasets.
