Normative XML Reference

Root Element exchange

This page describes the root element of the XML export file and all global metadata relevant for processing the export. The receiving system must evaluate the specifications at the root level before processing individual dealer or ad objects.

Page Goal Describe the global structure and processing logic of the export file.
Target Audience Integrators, developers of import interfaces, support.
Relevant Fields senderName, exportDate, transferMode, backLogDays, dealersDeleted, adsDeleted, dealers, validation

Structure Overview

Example Structure

<exchange>
  <senderName>...</senderName>
  <exportDate>...</exportDate>
  <transferMode>...</transferMode>
  <backLogDays>...</backLogDays>
  <dealersDeleted>...</dealersDeleted>
  <adsDeleted>...</adsDeleted>
  <dealers>...</dealers>
  <validation>...</validation>
</exchange>

Editorial Note

On the HTML page, this overview should be right at the beginning, supplemented by anchor links to the individual fields. Detailed processing of the contained payload occurs on the pages for dealer, ad, and contact.

Field Reference

exchange

Root element of the XML export file.

Type
Container element
Required
Yes
Contains
senderName, exportDate, transferMode, optional backLogDays, dealersDeleted, adsDeleted, dealers, optional validation
Processing Rule
The file is to be treated as a complete functional unit. Processing individual nodes without considering the root metadata is not sufficient.

senderName

Unique name of the file sender.

Type
String
Required
Yes
Meaning
Identifies the sending system or interface.
Processing Rule
The value should remain stable over the long term. Changes may result in known datasets no longer being correctly assigned or updated in the target system.

exportDate

Time of generation of the export file.

Type
Date/Time
Required
Yes
Meaning
Marks the creation time of the export.
Processing Rule
exportDate describes the file, not the modification time of individual objects. For object updates, the respective modified values are authoritative.

transferMode

Indicates the type of transfer.

Type
String
Required
Yes
Valid Values
full, update
Meaning
full stands for a complete synchronization, update for a change set.
Processing Rule
The receiving system must control the entire import logic based on this field.

backLogDays

Defines the lookback period for an update export.

Type
Integer
Required
No, only relevant for transferMode=update
Meaning
Specifies the period over which changes and deletions are included in the update.
Processing Rule
The field is only functionally relevant in the update context. It is not required for full exports.

dealersDeleted

Container for dealers deleted in the relevant period.

Type
Container element
Required
Yes, but can be empty
Meaning
In update exports, the element contains dealers deleted during the lookback period.
Processing Rule
In update mode, these dealers must be removed or deactivated in the target system. In full mode, the element is usually empty.

adsDeleted

Container for advertisements deleted in the relevant period.

Type
Container element
Required
Yes, but can be empty
Meaning
In update exports, the element contains deleted advertisements.
Processing Rule
In update mode, these advertisements are to be specifically deleted or deactivated in the target system.

dealers

Container for the transferred dealer objects.

Type
Container element
Required
Yes
Meaning
Contains the actual payload of the export in the form of dealer objects with their advertisements and contact persons.
Link
/interfaces/xml/dealer, /interfaces/xml/ad, /interfaces/xml/contact

validation

Optional section for validation information.

Type
Container element
Required
Optional
Meaning
The element is provided for in the schema and should therefore be documented, even if it is often less prominent operationally.
Editorial Recommendation
The HTML documentation should clearly state whether the element is actively used, can be ignored, or is intended for extensions.

Important: senderName is identification-relevant

senderName is not just descriptive information, but a technical key in the exchange context. A subsequent change can lead to known datasets no longer being correctly assigned.

Processing Logic at the Root Level

Rule 1: Evaluate Root First

Before processing dealer or ad objects, at least senderName, transferMode, and exportDate must be evaluated.

Rule 2: Mode Determines Import Strategy

With full, the file is to be treated as a complete target state. With update, the file is to be processed as a delta-oriented change set.

Rule 3: Interpret Deletion Containers Only in Functional Context

Empty deletion containers do not automatically mean that no inventory cleanup is required. In full mode, cleanup primarily results from the completeness of the delivered inventory.

Rule 4: Do Not Confuse Root Metadata with Object Metadata

exportDate refers to the file. modified refers to individual objects. For object updates, the respective object values are authoritative.

Notes and Pitfalls

Known Issue / Testing Note

The example XMLs are not fully schema-compliant in all respects. Such discrepancies should not be treated in detail on this page, but should be transparently documented on the /interfaces/xml/known-issues page.

Typical Implementation Error

transferMode is ignored and every file is treated as a full inventory. This leads to incorrect deletions and faulty synchronization states for update files.

Typical Interpretation Error

exportDate is used as a criterion for object updates. However, the respective object fields such as modified are authoritative for updates to individual datasets.
