Normative XML Reference

Prices, Media, and Additional Objects

This page bundles the cross-sectional XML components used in ads for pricing, media references, canonical URLs, and optional additional contexts. The goal is to make these elements documentable and reusable separately from the general ad structure.

Particularly Relevant for Integrators who process pricing logic, images, videos, external URLs, and optional extension objects.
Core Objects price, images, image, video, canonical_url, canonical_urls, auction, purchase

Cross-sectional Character

These objects occur in the context of ad, but are functionally independent enough to be described separately.

Normative and Operational Perspective

Even rarely used schema elements should remain documented as long as they are technically intended.

Implementation Goal

Target systems should adopt price and media structures as losslessly as possible so that later extensions or display rules can be supported.

Financials

price

Meaning

The element price describes the price of the ad. In addition to the actual numerical value, attributes for currency, tax logic, and if necessary, price units are used.

Attribute Meaning Note
currency Currency of the price, e.g., EUR. Store normatively, do not convert to free text.
taxtype Tax logic of the price, e.g., incl. or excl. VAT. Functionally relevant for display and further processing.
tax_percentage Tax rate as a decimal value, e.g., 0.190. Only interpret if taxtype supports this meaningfully.
price_unit Optional price unit, relevant e.g. for rental machines. Only use in functionally appropriate scenarios.

Important

A price value of 0 can functionally mean that no price was specified. This semantics should be deliberately handled in the target system and not automatically interpreted as a free offer.

Visuals

images and image

Meaning

The element images bundles the image references assigned to the ad. Below it, individual image elements are listed, which typically refer to retrievable image resources.

Special Features

In the XSD, images is intended as a structured media container. Additionally, the element can contain an attribute like md5, which can be used for integrity or change checks.

Aspect Description Note
Count Up to 30 images per ad are relevant in the functional context. The operational limitation should be considered during validation and import.
URL Rules (Opaque URL) Image URLs must be treated as opaque. The URL must not be manipulated or rewritten by deriving custom variants.
Caching & Updates Image changes strictly require new URLs/filenames for the changed image. Avoids faulty caching effects and guarantees image replacement.
Scopes & Variants Clear separation between ad images (under ad) and contact images (under contact). Logos or portraits do not belong in the ad image gallery.
Transport Methods The standard is transport as a retrievable HTTP URL. File-based transport (e.g., locally referenced images via ZIP) is optional and must be clarified in advance.
Integrity Feature Optional md5 at the container level. Can be used to efficiently check image inventories for changes.
Streaming

video

Meaning

The element video allows linking a video to the ad. In the documentation, a clear distinction should be made between video ID, video URL, and video type.

Attribute Meaning Note
video_id Unique identifier of the video within the referenced video system. Typically the central identifier for platforms like YouTube.
video_url Direct or embedded URL of the video. The use of this attribute should be checked against the operational implementation.
video_type Type of video, e.g., youtube. Should only be processed with documented values.
SEO

canonical_url and canonical_urls

Meaning

These elements serve to assign canonical target URLs to the ad. A distinction is to be made between a simple URL and a container with language-specific variants.

Multilingualism

Within canonical_urls, multiple canonical_url elements can be passed with a language attribute such as languages_iso_639_1.

Extensions

Additional Objects

auction

Optional additional object for auction scenarios. Even if this element is rarely used in daily business, it should be documented as long as it is provided for in the XSD.

purchase

Optional additional object for purchase scenarios. The functional use should be explicitly named, even if the operational relevance is currently low.

Logic

Processing Rules

Rule 1: Adopt Prices Structurally

Price value, currency, tax logic, and optional price unit should be stored separately so that the functional meaning is not lost.

Rule 2: Do Not Manipulate Image References

The delivered image URLs should be used unchanged. Avoid custom derivations from URL components.

Rule 3: Handle Media Changes Deliberately

Target systems should not view images and videos only as text fields, but should be prepared for change logic, replacement, and media updates.

Rule 4: Store Multilingual Canonical URLs Normatively

Language-related URL variants should not be merged into a single free text field.

Rule 5: Do Not Ignore Rare Additional Objects

Even rarely used elements such as auction or purchase should at least be stably recognized and documented to enable later extensions.

XML

Examples

Price Example

<price currency="EUR" taxtype="inclusive" tax_percentage="0.190">234567</price>

Example for Canonical URLs

<canonical_urls>
  <canonical_url languages_iso_639_1="de">https://example.invalid/de/ad/5001</canonical_url>
  <canonical_url languages_iso_639_1="en">https://example.invalid/en/ad/5001</canonical_url>
</canonical_urls>

Video Example

<video video_id="1F3nPCSG4Y0" video_url="https://www.youtube.com/embed/1F3nPCSG4Y0" video_type="youtube" />
Best Practices

Notes and Pitfalls

Typical Error: Price as Pure String

If the price is adopted without currency and tax logic, functionally important information is lost.

Typical Error: Deriving or Rewriting Image URLs

Changes to delivered image references often lead to import errors or unfindable media.

Typical Error: Merging Multilingual URLs

If canonical URLs of different languages are stored in an unstructured field, clean later output is hardly possible.

Documentation Note

Elements such as auction and purchase should explicitly remain in the documentation inventory despite low usage, as long as they are technically supported.
