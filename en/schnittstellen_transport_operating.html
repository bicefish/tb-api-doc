Operations

Transport and Operating Model

This documentation describes the operational aspects of the integration with technikboerse, including transfer methods, authentication procedures, and the onboarding process for partners and dealers.

Options

Supported Transfer Methods

There are two primary ways to transfer listings to the technikboerse system:

A. XML File

XML is a file-based integration method. Processing occurs in batch mode (not instantaneous).

Partner → technikboerse (Sending data)

  • Upload: The partner uploads the XML file via FTPS to the technikboerse server.
  • Pull: The partner hosts the file at a URL, which technikboerse retrieves regularly.

technikboerse → Partner (Receiving data)

  • Upload by technikboerse: technikboerse uploads the file to a partner's FTPS server at agreed times.
  • Retrieval by Partner: The partner retrieves the file from an FTPS server provided by technikboerse.

B. REST API

The REST API allows direct communication and real-time synchronization between systems.

  • Changes are applied immediately.
  • Ideal for partners requiring a high level of data freshness.
  • View REST API Overview
Security

Authentication and Access

Valid credentials are required for production integration:

XML via Upload / Pull

Depending on the direction and variant (see above), FTPS access is required. Specific details regarding host, ports, and encryption methods are provided to partners during technical onboarding.

REST-API

An API key with write permissions is required. Details on token management and refresh flows are also provided during the onboarding phase.

Identification

Matching and Identification

Record assignment follows fixed rules:

Standard: GUID

Ads have a unique GUID. This GUID is looked up during import. If it is not found, a new record is created.

Change Detection: md5

An md5 checksum is generated for the entire record. If it differs from the stored value, the ad is updated.

Special Cases

Depending on the integration type, matching can also occur via Dealer ID or an external customer/system ID.

Data Sovereignty & Conflict Handling

Typically, one system (either technikboerse or the partner system) is defined as leading. Manual changes on technikboerse should be avoided if a partner system provides data, as these may be overwritten during the next import.

Simultaneous edits via XML/API and the manual interface are rare but can lead to unforeseen states. It is recommended to make changes primarily in the leading system.

Sync Logic

Update and Full Mode

The choice of mode has significant impacts on the data set:

Update Mode

Transfers only changes (added or modified ads) and explicit deletions.

  • Deletions are explicit via <deletedAds> or <deletedDealers>.
  • Deleting a dealer automatically removes their ads.
  • Uses a "Lookback Window" for changes (see Operational Rules).

Full Mode

Transfers the entire active inventory. The delivery is considered the complete inventory for this interface.

  • Deletions occur implicitly by absence: Ads not included in the XML for this interface are deleted.
  • The dealer itself is not automatically removed.

Warning: Mode Selection

Switching between Full and Update without coordination can lead to unintended mass deletions. See Deletion Logic for details.

Governance

Operational and Processing Rules

For a stable and synchronous data exchange, the following operational guidelines apply:

Lookback / Backlog Window (Update Mode)

When generating update files, a safety time window (overlap) into the past should be included (e.g., changes from the last 48 hours for daily exports). This ensures no changes are lost due to short-term outages or timing overlaps.

Resynchronization

To prevent "drift" (creeping inconsistencies) in update mode, it is strongly recommended to perform a periodic full synchronization (e.g., once a week). This synchronizes the entire inventory and cleans up obsolete records.

Processing Order & File Handling

Files are processed strictly chronologically. File names must include a timestamp (e.g., export_20260422_1530.xml or exchange_20260422_1530.xml) to ensure correct ordering. After successful processing, files on the target system are archived or removed.

Processing Cadence

The cadence of data exchange (e.g., daily at 02:00 AM or twice daily) must be agreed on for each project in order to control the load on both systems.

Setup

Onboarding a New Connection

The technical onboarding process follows these steps:

1

Staging & Sandbox

Establish access to the sandbox system. Since there is no explicit "dry-run" mode for XML uploads, this environment serves for extensive integration testing before going live.

2

Test Account

Create test dealers and access credentials.

3

Parameter Provisioning

Transfer API keys, FTPS access data, dealer IDs, and preview URLs.

4

Validation

Test the integration in the staging system.

5

Approval

Approve the integration for live operation.

6

Go-Live

Provide the production access details.

Policy

Operational Notes and Limits

Please note the following operational constraints:

For general integrations, no binding standards (SLA/SLO) are currently documented for:

  • Guaranteed response or processing times
  • Retry strategies and timeouts
  • Rate limits or maximum file sizes

If these parameters are critical for your specific integration, they must be coordinated on a project basis.

Stability

Error and Exception Cases

Common operational states during import:

conflict / foreign / derivation

The dealer is already assigned to a different derivation. The import may be rejected and requires manual verification of responsibility.

locked / deleted

The dealer is deactivated or blocked in the target system. In this case, ads will not be imported.

Monitoring & Error Logging

XML: Processing errors are only detected during the import process. Local validation against the XSD schema before upload is strongly recommended.

REST API: The success of a call is immediately signaled via the HTTP response. Applications should log and evaluate these responses to identify integration errors promptly.
