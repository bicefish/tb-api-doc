Operations

Transport and Operating Model

This documentation describes the operational aspects of the integration with technikboerse, including transfer methods, authentication procedures, and the onboarding process for partners and dealers.

Supported Transfer Methods

There are two primary ways to transfer listings to the technikboerse system:

A. XML File

XML is a file-based integration method. Processing occurs in batch mode (not instantaneous).

  • Upload: The partner uploads the XML file via FTPS to the technikboerse server.
  • Pull: The partner hosts the file at a URL, which technikboerse retrieves regularly.

B. REST API

The REST API allows direct communication and real-time synchronization between systems.

  • Changes are applied immediately.
  • Ideal for partners requiring high data currency.
  • View REST API Overview

Authentication and Access

Valid credentials are required for production integration:

XML via Upload

FTPS access is required. This must be requested from the Development or Product Management department.

REST-API

An API key with write permissions is required. Application is also handled via Development or Product Management.

Processing Model and Frequency

Transfer Method Processing Latency Typical Use Case
XML File-based / Batch 1x daily Periodic full or differential data
REST Request-based Immediate Real-time synchronization

Matching and Identification

Record assignment follows fixed rules:

Standard: GUID

Ads feature a unique GUID. This is searched for during import. If it doesn't exist, a new record is created.

Change Detection: md5

An md5 checksum is generated for the entire record. If it differs from the stored value, the ad is updated.

Special Cases

Depending on the integration type, matching can also occur via Dealer ID or an external customer/system ID.

Update and Full Mode

The choice of mode has significant impacts on the data set:

Update Mode

Transfers only changes (added or modified ads) and explicit deletions.

  • Deletions are explicit via <deletedAds> or <deletedDealers>.
  • Deleting a dealer automatically removes their ads.
  • Uses a "Lookback Window" for changes (see Operational Rules).

Full Mode

Transfers the entire active inventory. The delivery is considered the complete inventory for this interface.

  • Deletions occur implicitly by absence: Ads not included in the XML for this interface are deleted.
  • The dealer itself is not automatically removed.

Warning: Mode Selection

Switching between Full and Update without coordination can lead to unintended mass deletions. See Deletion Logic for details.

Operational Rules

For a stable and synchronous data exchange, the following operational guidelines apply:

Lookback / Backlog Window (Update Mode)

When generating update files, a safety time window (overlap) into the past should be included (e.g., changes from the last 48 hours for daily exports). This ensures no changes are lost due to short-term outages or timing overlaps.

Resynchronization

To prevent "drift" (creeping inconsistencies) in update mode, it is strongly recommended to perform a periodic full transfer (e.g., once a week). This synchronizes the entire inventory and cleans up orphaned records.

Processing Order & File Handling

Files are processed strictly chronologically. File names must include a timestamp (e.g., export_20260422_1530.xml) to ensure correct ordering. After successful processing, files on the target system are archived or removed.

Processing Cadence

The frequency of data exchange (e.g., daily at 02:00 AM or twice daily) must be agreed upon on a project basis to manage the load on both systems effectively.

Onboarding a New Connection

The technical commissioning process follows these steps:

  1. Staging Access: Establish access to the sandbox system.
  2. Test Account: Create test dealers and access credentials.
  3. Parameter Provisioning: Transfer of API keys, FTPS data, Dealer IDs, and preview URLs.
  4. Validation: Test the integration in the staging system.
  5. Approval: Release for live operations.
  6. Go-Live: Provision of production access.

Operational Notes and Limits

Please note the following operational constraints:

For general integrations, no binding standards (SLA/SLO) are currently documented for:

  • Guaranteed response or processing times
  • Retry strategies and timeouts
  • Rate limits or maximum file sizes

If these parameters are critical for your specific integration, they must be coordinated on a project basis.

Errors and Exceptions

Common operational states during import:

conflict / foreign / derivation

The dealer is already assigned to a different derivation. The import may be rejected and requires manual verification of ownership.

locked / deleted

The dealer is deactivated or blocked in the target system. In this case, ads will not be imported.
