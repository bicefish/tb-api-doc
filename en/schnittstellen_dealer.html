Normative XML Reference

Element dealer

The element dealer represents a dealer or provider within the XML interface. It bundles the technical identity of the dealer, its master data, as well as the associated advertisements and contacts. For the target system, dealer is the central link between the provider, inventory, and contact persons.

Page Goal Technically and functionally define dealer objects uniquely.
Particularly Relevant for Integrators who process dealer records, advertisements, and contact persons together.
Core Content guid, id, pguid, info, created, modified, ads, contacts

Structure and Classification

Structure Sketch

<dealers>
  <dealer guid="..." id="..." pguid="...">
    <info>...</info>
    <phone>...</phone>
    <mobile>...</mobile>
    <fax>...</fax>
    <created>...</created>
    <modified>...</modified>
    <ads>...</ads>
    <contacts>...</contacts>
  </dealer>
</dealers>

Functional Role

dealer represents a provider with an independent technical identity. 0 to n advertisements and 0 to n contact persons are assigned to it.

Technical Role

The target system uses guid and, if necessary, id to uniquely assign dealer objects and find them again during updates.

Relationship to Other Objects

Below the dealer object, advertisements are listed in ads and contact persons in contacts.

Attributes of dealer

Attribute Meaning Required Note
guid Unique technical identification of the dealer. Yes Decisive for stable assignment in the target system.
id Internal ID of the dealer object in the sending system. Optional depending on schema, functionally recommended Should be transferred as an additional reference even if the GUID is primary.
pguid Additional referencing GUID, if used in the data model. Optional Only document and evaluate if this relationship is functionally actively used.

Important: Do Not Confuse GUID and ID

For functionally stable identification of the dealer, the guid is decisive. The id is an additional reference to the sending system and can differ in its meaning from implementation to implementation.

Processing Rules

Rule 1: Locate Dealer via GUID

The target system should identify dealer objects primarily via guid. This keeps the assignment stable even during internal reorganizations in the sending system.

Rule 2: Evaluate Changes via modified

During update processing, modified is the decisive field for determining whether a dealer object needs to be updated.

Rule 3: Process Sub-objects in Dealer Context

Advertisements and contacts are functionally in the context of the dealer. Isolated processing without reference to the parent dealer can lead to inconsistencies.

Rule 4: Observe Deletion Logic Separately

The processing of a dealer object must not be confused with deletion logic. Deleted dealers are signaled via the mechanisms described on the Deletion Logic page.

Example

Minimal Example

<dealer guid="dealer-1001" id="1001">
  <info>
    ...
  </info>
  <phone>+49 123 456789</phone>
  <mobile>+49 171 1234567</mobile>
  <fax>+49 123 456780</fax>
  <created>2024-01-01T09:00:00</created>
  <modified>2024-05-12T06:00:00</modified>
  <ads>
    ...
  </ads>
  <contacts>
    ...
  </contacts>
</dealer>

Interpretation

The example shows a dealer with technical identity, communication data, and sub-objects. In the target system, the dealer itself should first be assigned or created before processing the associated advertisements and contacts.

Notes and Pitfalls

Typical Error: Linking Dealer Only via id

If only the sender's internal ID is used, incorrect assignments can occur if changes are made in the source system. The GUID should be used primarily.

Typical Error: Ignoring modified

If dealer objects are blindly overwritten with every import, it can create unnecessary load or unintentionally overwrite local corrections.

Differentiation

Communication data at the dealer level is not identical to contact person data at the contact level. Both levels should be cleanly distinguished in the target system.
