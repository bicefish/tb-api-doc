Operational Discrepancies and Special Features

Known Issues

This page collects known discrepancies between XSD, example XMLs, and existing documentation. It is not a substitute for the normative reference, but an operational supplementary area for integrators, support, and quality assurance.

Particularly Relevant for Integrators, support, testing, validation, and editorial maintenance of the documentation.
Basic Principle Discrepancies are documented transparently and not silently smoothed over.

Purpose and Usage

Normative vs. Operational

The normative reference from XSD and the functionally approved rules remains authoritative for the XML structure. Known Issues documents deviations from this.

Goal

Integrators should recognize early where examples, legacy documentation, or existing behavior do not completely match the target structure.

Maintenance

Each entry should contain status, impact, and recommendation. Cleared points can be transferred to the changelog and archived or removed here.

Important

Known Issues are not an alternative specification. An entry on this page does not automatically mean that a discrepancy is functionally intended or technically permanently permissible.

Issue List

Topic Status Affected Source Description Impact Recommendation
mobile vs. mobil Known issue XSD and Example XMLs In the XSD, the field mobile is defined at the Contact level. In the available Full and Update examples, mobil is used instead. The example XMLs are not completely schema-compliant in this point. Validations and parsers can therefore react differently. Document mobile normatively, report the observed spelling mobil additionally as a known discrepancy, and deliberately check during implementations.
Update examples without meaningful deletion cases Doc Gap Example XMLs The available example XMLs show the Update structure but do not illustrate central deletion cases in a didactically sufficient form. Developers see the structure, but not all relevant functional variants of the deletion logic. Provide supplementary minimal examples for deleted dealers and ads in the HTML documentation.
validation in XSD, but operationally not very visible Open XSD and Legacy Documentation The element validation is provided for in the XSD, but plays only a minor role in the previous documentation and operational description. Integrators cannot reliably assess whether the element is actively used, can be ignored, or is only reserved for extensions. Explicitly clarify the functional status and document it on the reference page.
auction and purchase present, but hardly explained Doc Gap XSD and Legacy Documentation The elements are technically present, but are explained only to a limited extent or not at all in the evolved documentation. Unclear treatment in target systems, although later use or extension is possible. Document as optional additional objects in the HTML documentation and state their current functional status.
Free text instead of reference structure in legacy document Doc Gap Legacy Documentation Much content is functionally present but not maintained field-specifically, not anchor-capable, and not modularly. Increased interpretation effort and hindered online usage. Transfer content to HTML-native reference pages with a uniform field and rule structure.
Example behavior can be misunderstood normatively Open Example XMLs and Doc Usage Example XMLs are often read by integrators as technically binding references, although they may contain operational or historically conditioned special features. Incorrect implementation decisions if examples are interpreted uncritically as a norm. Clearly distinguish between normative reference and illustrative example in all example pages.

Business-Critical Point

The discrepancy mobile vs. mobil is not just an editorial blemish, but can have direct effects on validation, parsing, and data adoption. This point should be visible early in integration projects.

Examples

Normative Target Spelling according to XSD

<contact id="12">
  <mobile>+49 171 1234567</mobile>
</contact>

Observed Spelling in Example XMLs

<contact id="12">
  <mobil>+49 171 1234567</mobil>
</contact>

Recommendations for Implementation and Maintenance

Recommendation 1: Prioritize XSD as Technical Reference

In case of discrepancies between XSD and examples, the technical target structure should first be derived from the XSD, unless a functionally approved counter-rule exists.

Recommendation 2: Provide Examples with Comments

Example pages should not just show raw XML, but should visibly mark discrepancies, simplifications, and didactic reductions.

Recommendation 3: Version Known Issues

Each entry should be maintained with date, status, and responsibility, so it remains clear whether the point is still active, clarified, or already cleared.

Recommendation 4: Separate Validation and Documentation

A discrepancy can be operationally known without it being permanently permissible. Documentation and validation strategy should therefore be deliberately coordinated with each other.
